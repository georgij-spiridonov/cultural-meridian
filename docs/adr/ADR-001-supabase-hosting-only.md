# ADR-001. Supabase используется только как хостинг PostgreSQL, схемой владеет Alembic

**Статус:** принято, 2026-11-13

## Контекст

Команда хочет использовать Supabase. ТЗ требует запуска через `docker compose up` на чистой машине не дольше 10 минут (раздел 10) и обязательного локального сценария при нестабильном внешнем доступе (раздел 11). REST API, OpenAPI и виджет уже обеспечивает FastAPI. Модераторы входят через собственную таблицу `moderators` (вход по паролю, сессия в подписанной cookie).

## Решение

Supabase служит только управляемым хостингом PostgreSQL для развёрнутого демонстрационного контура. Приложение подключается к нему через `DATABASE_URL` так же, как к любому PostgreSQL. По умолчанию `docker-compose.yml` поднимает локальный `postgres:17`. Схемой, расширениями (`pg_trgm`, `unaccent`) и данными владеют SQLAlchemy 2.0 и Alembic. `supabase-py`, PostgREST, Supabase Auth, Storage и Realtime не используются.

## Рассмотренные альтернативы

- **Облачный Supabase везде, без локальной БД.** Отклонён: демонстрация зависела бы от сети, а бесплатный проект засыпает после 7 дней без активности.
- **Self-hosted Supabase в compose.** Отклонён: около 10 дополнительных контейнеров ставят под угрозу запуск за 10 минут, а их возможности проекту не нужны.
- **PostgREST и Supabase Auth.** Отклонены: PostgREST дублирует контракт `/api/v1` и обходит сервисный слой с проверками, Auth избыточен для 2–3 модераторов.

## Последствия

- Пулер Supabase в режиме transaction не поддерживает prepared statements. Приложение подключается к нему через asyncpg с `statement_cache_size=0`, а Alembic подключается напрямую или через пулер в режиме session.
- Код не должен опираться на особенности Supabase (RLS-политики, схема `auth`, триггеры Supabase). Тогда хостинг можно сменить заменой `DATABASE_URL`.
